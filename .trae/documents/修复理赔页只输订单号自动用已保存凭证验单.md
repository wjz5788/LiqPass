**问题与目标**

* 现状：理赔页验证在 `USE_JP_VERIFY=1` 时走直接调用日本服务的分支，不携带用户 API 密钥，OKX 订单查询会失败。

* 目标：理赔页只需输入 `ordId`，后端自动读取并解密用户在“API 设置”页保存的 OKX 凭证，统一通过后端代理 `/api/v1/verify` 转发到日本服务器完成验证，不影响其他模块。

**当前实现要点**

* 理赔入口：`apps/us-backend/src/routes/claims.ts:POST /claims/verify` → `claimsService.verifyClaim`。

* 核心分支：`apps/us-backend/src/services/claimsService.ts:275` 起

  * `USE_JP_VERIFY=1` → `verifyViaJpServer(...)`（不带密钥）`apps/us-backend/src/services/claimsService.ts:426`。

  * 否则 → `triggerExternalVerification(...)`（自动取密钥，走后端代理）`apps/us-backend/src/services/claimsService.ts:476`。

* 后端代理：`apps/us-backend/src/routes/okx-verify.ts:57` 起的 `POST /api/v1/verify`，内部调用日本服务器，并保存 `verify_results` 与证据。

* 凭证管理：`apps/us-backend/src/services/apiKeyService.ts:106`、`256` 处展示了取库、解密与调用统一验证的方式。

**改造方案**

* 固定走“自动取密钥 + 后端代理”路径：在 `verifyClaim` 内移除/忽略 `USE_JP_VERIFY` 分支，始终调用 `triggerExternalVerification(orderRef, order.pair, userId)`。

  * 自动读取并解密用户最新 `api_keys` 记录（仅一份凭证），未找到则返回 `API_KEY_NOT_FOUND`。

  * 代理请求 `POST /api/v1/verify`，最终由 `jpVerifyClient` 调用日本服务器，保持证据与 `verify_results` 的落库。

* 保持现有证据与审计逻辑：理赔服务仍从 `verify_results` 读取最新结果，生成理赔判定并记录审计事件，既有结构不变。

* 交易对规范：代理层已有 `normalizeInstId(...)`（`apps/us-backend/src/routes/okx-verify.ts:33`），确保 `BTC-USDT-SWAP`/`BTC-USDC-SWAP` 一致性，无需前端再输入 `instId`。

**范围控制（不影响其他模块）**

* 只改 `claimsService.verifyClaim` 的分支选择；不改路由签名、返回结构、数据库结构、前端表单字段、凭证保存逻辑。

* 不改 `jpVerifyClient`、不改 `okx-verify` 路由、不中断 API 设置页现有流程。

**验证与回归**

* 前置：在“API 设置”页保存一次 OKX `apiKey/secretKey/passphrase/uid`。

* 流程：理赔页仅输入 `ordId`，调用 `/api/v1/claims/verify`；后端自动使用用户凭证拉取订单，并生成 `evidence` 与 `verify_results`。

* 检查：

  * 数据库存在最新 `verify_results`（按 `ord_id` 排序）供理赔读取。

  * 证据文件在 `apps/jp-verify/reports/evidence/...`（已存在示例）。

  * 两个交易对都通过：`BTC-USDT-SWAP` 和 `BTC-USDC-SWAP`。

**环境与配置**

* 理赔路径不再依赖 `USE_JP_VERIFY`；可设为 `0` 或忽略其对理赔的影响。

* 保留 `JP_VERIFY_BASE_URL|JP_VERIFY_BASE` 指向日本服务器；`ALLOWED_ORIGINS`、鉴权等沿用现有配置。

**回滚策略**

* 单文件小改动，若需回退可快速恢复到原分支逻辑。
